# Mametas coherence system

This document is the maintenance contract for the post-October 2026 Mametas site.

## Principle

Mametas is still a static site assembled by several historical materialisation scripts. The coherence layer runs **last**. Older generators may continue to produce legacy markup, but the final build must normalize the public output before deployment.

Do not add new one-off header/footer/navigation patches to individual pages. Fix the shared source or one of the final normalization passes instead.

## Final build order

1. Historical/editorial materialisation.
2. Presentation compilation.
3. `v6_preserve_sources_dates_credits_2026_10_02.py`
   - preserves visible checked dates before legacy footers are replaced;
   - normalizes formal source headings;
   - standardizes existing photo-credit captions;
   - adds credits only when repository metadata explicitly identifies the author/source.
4. `v6_coherence_envelope_2026_10_02.py`
   - one header;
   - one mobile navigation;
   - one footer;
   - exact FR/EN pair when known;
   - shared `mametas-shell-v1.css`.
5. `v3_destination_reality_layer_2026_09_25.py`
   - all 9 destination pages;
   - canonical top;
   - one Reality Check vocabulary;
   - Riviera Fit and Hotel Fit bridges.
6. `v6_city_card_system_2026_10_02.py`
   - Home + Places city decision surfaces;
   - 6 bases / 3 detours;
   - canonical tags and city names.
7. `v6_hotel_detail_normalization_2026_10_02.py`
   - all full hotel reviews and generated Hotel Take pages;
   - canonical parent link, eyebrow, facts vocabulary, booking CTA and next decision.
8. `v6_semantic_cleanup_2026_10_02.py`
   - closed CTA vocabulary and known language leaks only.
9. `v6_detail_family_top_normalization_2026_10_02.py`
   - Practical legacy URLs, Beaches and comparison-page tops.
10. `v6_content_family_normalization_2026_10_02.py`
    - Restaurants;
    - Beaches;
    - Art & Culture;
    - Good Finds / Bons Plans;
    - local hotel-review links.
11. `v6_plan_family_normalization_2026_10_02.py`
    - Plan siblings use one page-top system and hero-image treatment.
12. Validators:
    - `validate_v6_coherence_envelope_2026_10_02.py`
    - `validate_v6_content_coherence_2026_10_02.py`

Deployment must not start if either validator fails.

## Canonical city data

`data/city-system-v1.json` is the single source for the nine core destination decisions.

### Bases

- Nice
- Villefranche & Cap-Ferrat
- Antibes
- Cannes
- Monaco
- Menton

### Detours

- Èze
- Saint-Paul-de-Vence
- Saint-Tropez

The file owns:

- canonical EN/FR name;
- route;
- image;
- alt text;
- “best for” tag;
- short Home description;
- Reality Check values.

Do not hard-code a competing “Best for” or mobility sentence in a new city component. Read from the canonical data or extend the normalization pass.

## Shared envelope

Canonical English navigation:

`Plan · Places · Stay · Explore · Practical`

Canonical French navigation:

`Préparer · Destinations · Dormir · Explorer · Pratique`

No main navigation item should point to a homepage anchor. Contextual journeys belong inside the page body.

The footer is generated by the global shell. Do not create contextual footer variants.

## Detail-page top

Every detail page uses:

1. named parent return link;
2. `TYPE · SUBJECT` eyebrow;
3. editorial H1;
4. standfirst/lead;
5. Mametas Checked badge when the page carries verified practical information.

Avoid breadcrumbs as a second navigation grammar.

## Destinations

Every destination must end the build with:

- one canonical top;
- one Reality Check;
- `Getting around / Budget / Season / Logistics` or FR equivalent;
- Riviera Fit CTA;
- Hotel Fit bridge for the six base destinations;
- one next-decision layer;
- canonical Sources checked heading.

Èze keeps its explicit Èze-sur-Mer / Èze Village warning in addition to the Reality Check.

## Hotels

A full review uses:

- parent hotel-list link;
- `HOTEL · CITY`;
- hotel name;
- Area / Format / Best for / Budget;
- The Mametas Verdict;
- Why we keep it;
- Who it suits;
- Mèfi — watch out if…;
- provider-specific affiliate CTA;
- The next decision;
- Sources checked / checked date.

Allowed booking labels:

- `Check rates on Booking.com`
- `Check rates on Expedia`
- `Voir les tarifs sur Booking.com`
- `Voir les tarifs sur Expedia`

Do not replace or rebuild affiliate URLs while changing visible labels.

The legacy `/en/hotels/nice/` and `/hotels/nice/` hub URLs redirect to the canonical Nice chooser and must not re-enter the sitemap.

## Restaurants

Restaurant detail cards converge on:

- H3 restaurant name;
- compact decision metadata: price · cuisine · area when source text supports it;
- existing description and catch;
- address;
- external source;
- Open map.

Do not call Michelin or a tourism-office page an “official restaurant source”. The normalizer preserves a generic Source label in that case.

## Beaches

Beach cards converge on:

- H3 beach name;
- area;
- description;
- facts with Type / Access / Services first when those facts exist;
- 2026 prices grouped when the page already contains price data;
- Open map;
- official source where available.

Do not invent missing sand/pebble/accessibility data to fill a component.

## Art & Culture

Culture pages use the common practical grid:

- Address
- Getting there
- Time needed
- Hours & price
- Booking / official information

When a source page does not actually state one of those facts, the component points the reader to the official information rather than manufacturing a value.

Editorial section names:

- Why we go
- What to actually look at
- Sources checked

FR equivalents stay French. `Mametas Checked`, `Riviera Fit`, `Hotel Fit` and `They know the Riviera.` remain brand names.

## CTA vocabulary

Internal:

- Try Riviera Fit →
- Run my profile through Riviera Fit →
- Try Hotel Fit →
- Choose a hotel in {Town} with Hotel Fit →
- Read our full review →
- Open map is not internal; see below.

External:

- Open map ↗
- Official source ↗
- Source ↗ where the destination is an independent third party.

FR follows the same distinction.

## Sources, dates and photo credits

Formal source blocks are:

- `Sources checked`
- `Sources vérifiées`

A checked date is preserved in the page body before the old footer is removed.

Photo credits are only added automatically when the repository carries explicit attribution metadata. Current automated sources include:

- the Depositphotos Nice practical manifest;
- Renaud's own Nice photo bundle;
- explicit known author filenames already documented in the audit.

Do not infer a photographer from an image subject.

## Safe change rule

Before adding a new component or page family, ask:

1. Is there already a shared component that serves this function?
2. Is the same information already canonical in a data file?
3. Will a final normalization pass overwrite this markup?
4. Does the page need a genuinely different component, or is it merely another historical variant?
5. Can the validator express the rule so it cannot drift again?

Prefer one source + one renderer + one validator over another one-off page patch.
