# Mametas UX Adoption Journey

## North star

Mametas should feel simpler than the amount of intelligence it contains.

The product sequence is:

**Trust -> decision -> action -> monetisation.**

Affiliate revenue is a consequence of a recommendation the user already understands and trusts. It must never be the reason a recommendation appears to exist.

## The four-step journey

1. **Choose the base**
   - Primary product: Riviera Fit
   - Manual alternative: Places
   - User question: "Where should I stay?"
   - Success state: one base feels justified, with trade-offs understood.

2. **Choose the hotel**
   - Primary product: Hotel Fit
   - Manual alternative: Stay / base hotel pages
   - User question: "Which hotel fits this trip?"
   - Success state: a short list with role, reason and catch.

3. **Fill the days**
   - Primary surfaces: Explore, destination guides, short itineraries
   - User question: "What is actually worth doing?"
   - Success state: a small number of high-confidence experiences, not a checklist.

4. **Make it work**
   - Primary surfaces: Practical, transport, weather, booking notes, Right Now
   - User question: "How do I execute this without friction?"
   - Success state: logistics are clear enough to act.

## Homepage role

The homepage is not the site map. It is the shop window and adoption ramp.

It should communicate, in this order:

1. What Mametas is.
2. The four-step journey in one glance.
3. Riviera Fit as the preferred shortcut to step 1.
4. A manual Places route for users who want to browse.
5. Stay / Hotel Fit only after the base idea has been introduced.
6. A small edit of experiences.
7. Current information and credibility.

The homepage must not expose every taxonomy or every capability.

## Product hierarchy

### Riviera Fit
Purpose: choose the base.

- Strongly identifiable.
- Light visual container; colour concentrated in CTA and active states.
- On Home: one compact example, explicitly labelled as an example.
- On Plan: full interactive questionnaire.
- Result must lead naturally to Hotel Fit with the base preselected.

### Hotel Fit
Purpose: choose the hotel once geography is known.

- Same product grammar as Riviera Fit.
- Different functional accent colour.
- On Home: visible inside Stay, not staged as a second hero.
- On destination and Riviera Fit results: contextual next action.
- Affiliate links appear only after editorial fit/reason/catch is visible.

## Visual hierarchy

Every component belongs to one of four levels.

### L1 - Decision
One dominant question, verdict or primary action.
Examples: "Stay in Nice", "Start Riviera Fit", "Find my hotel with Hotel Fit".

### L2 - Evidence
Why the decision makes sense.
Examples: trade-offs, reality check, short alternatives.

### L3 - Utility
Information needed to execute.
Examples: train time, address, map, opening hours, booking requirement.

### L4 - Depth
Optional material for users who want more.
Examples: methodology, sources, long context, further reading.

Large colour fields and large typography are reserved for L1. Photography creates desire or orientation; it does not decorate empty space.

## Affiliate rule

Affiliate CTAs belong at the point of **decision readiness**, not at the point of discovery.

### Hotel pages
Editorial verdict -> role -> catch -> practical facts -> **Check rates / book**.

### Hotel Fit
Criteria -> shortlist -> why each fits -> catch -> **rate links**.

### Activities / booking pages
Why it is worth booking -> when advance booking matters -> **affiliate option**.

### Generic editorial / practical pages
No affiliate CTA unless booking is a natural next step.

Disclosures remain clear and visible, but monetisation must not dominate the visual hierarchy.

## Contextual next-step logic

Do not end a page with generic navigation when a logical next action is known.

Examples:

- Destination page -> "Staying here? Run Hotel Fit with this base."
- Riviera Fit result -> "Base chosen. Now choose the hotel."
- Hotel page -> "Compare other hotels in this base" + rate CTA.
- Beach page -> "Need the rest of the day? Explore nearby."
- Practical page -> return to the decision it helps execute.

## Entry from Google

Every deep page must work as a front door.

Within the first screen or first meaningful block, a user should understand:

1. Where they are.
2. What Mametas recommends or explains.
3. The next logical action.

The global four-step journey can be signposted lightly, but must not become repetitive chrome.

## Phase order

### A. Global adoption layer
- Homepage journey spine.
- Product visual grammar.
- Primary / secondary CTA rules.
- Tool naming parity.

### B. Hub adoption
- Plan, Places, Stay, Explore, Practical.
- One dominant job per hub.
- One clear next action.

### C. Template adoption
- Destination, hotel, beach, culture, practical, itinerary.
- Verdict first.
- Contextual exits.
- Affiliate readiness.

### D. Final QA
- Mobile scroll weight.
- FR/EN parity.
- Performance.
- Accessibility.
- Broken links and stale naming.
- Visual polish only after the hierarchy is stable.

## Measure of success

A first-time visitor should be able to answer, without reading the whole page:

- What decision is this page helping me make?
- What does Mametas think?
- What should I do next?

If those three answers are obvious, the page is doing its job.
